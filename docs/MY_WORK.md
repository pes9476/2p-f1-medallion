# 박은서의 F1 Team Builder 작업 상세 기록

> 팀 프로젝트 F1 Team Builder Intelligence에서 제가 맡은 작업을 **기획 → 문제 → 해결 → 결과** 순서로 정리한 문서입니다.
> 각 작업 끝의 **"설명 포인트"**는 이 작업을 다른 사람에게 설명할 때 꼭 알아야 하는 개념입니다.
>
> 개발 방식: 문제 정의, 설계, 결과 검수는 직접 했고, 코드 구현에는 AI 코딩 도구를 함께 활용했습니다.

---

## 0. 프로젝트 진행 방식

- 팀끼리 데이터를 교환하는 방식이었습니다. 우리 팀이 주제(F1)와 데이터를 상대 팀에 넘기면, 상대 팀이 데이터를 **일부러 망가뜨려(오염)** 돌려줍니다. 우리 팀은 그 오염 데이터를 정제해서 분석까지 이어갑니다.
- 데이터는 **메달리온 구조**로 관리했습니다.
  - **Bronze**: 받은 그대로의 원본(오염 데이터)
  - **Silver**: 오염을 검사·복구·검증하고 MySQL에 적재한 데이터
  - **Gold**: 화면과 의사결정에 바로 쓰는 요약 지표

### 설명 포인트
- **메달리온 아키텍처**: 데이터를 품질 단계별로 나눠 저장하는 방식. 단계마다 따로 검증하고 다시 만들 수 있어서, 문제가 생겼을 때 어느 단계에서 틀렸는지 찾기 쉬움

## 1. 오염 데이터 1차 복구 파이프라인 (Bronze → Silver)

### 기획
상대 팀이 보낸 오염 데이터 6종(sessions, drivers, laps, stints, weather, pit)을 분석에 쓸 수 있는 상태로 복구해야 했습니다.

### 작업
- 원본 명세서와 파일 간 관계(공통 키 `session_key`, `driver_number`)를 기준으로 비어 있거나 틀린 값을 찾았습니다.
- **근거가 있는 값만** 복구했습니다. 예를 들어 drivers·laps의 경기 장소 정보가 비면, 같은 `session_key`의 sessions 행에서 가져왔습니다.
- 원본값은 `original_*` 컬럼으로 남기고, 고친 칸마다 아래 4가지를 기록했습니다.
  - `repair_status`: 복구 여부
  - `repair_method`: 복구 방법 (예: `session_key_join`)
  - `repair_confidence`: 신뢰도 (HIGH 등)
  - `repair_reason`: 사람이 읽을 수 있는 이유
- 결과물: 복구 CSV 6종, 컬럼별 요약(`repair_summary.csv`), 행 단위 근거(`repair_detail.csv`), HTML 품질 리포트

### 이후
팀원이 이 구조를 진단코드 27종, 154개 검증 규칙 체계로 고도화했습니다. 최종 결과는 탐지 28,071건 중 근거 있는 1,357셀만 복구, 정제 전 FAIL 12건 → 정제 후 0건입니다.

### 설명 포인트
- **왜 평균·중앙값으로 채우지 않았나**: 통계값으로 채우면 원래 비어 있는 게 정상인 값(예: 1랩 랩타임)까지 가짜 값이 되어 분석이 왜곡됨
- **데이터 계보(lineage)**: 원본값과 복구 이유를 함께 남겨 두면, 나중에 "이 숫자 어디서 왔어?"에 답할 수 있음

## 2. 분석 화면 디자인 시안

### ① Team Builder Insight Report (`design/index.html`)
- 분석 결과를 리포트처럼 읽히게 구성: **핵심 질문 → 짧은 답 → 근거 수치 3개 → 장별 상세(팀 진단, 라인업 격차, 영입 후보, 피트 운영, 신뢰도와 한계, 권고)**
- 대시보드 첫 시안을 이 리포트 형태로 전면 개편

### ② Decision Board C안 (`design/variants/C_decision_board.html`)
- 최종 통합 기획안 기준으로 작성
- 분석 전 세운 가설을 **"처음 생각"**으로, 데이터 결과를 **"실제 결과"**로 카드마다 나란히 배치하고 O / X / ? 로 판정
- 100점 종합점수 대신 **실제 기록 + 상위 %**로 후보 비교
- 추가 데이터 5종의 쓰임새(본경기 포인트, 출발→결승 순위 변화, 세이프티카 구간 제외, 피트 손실)와 데이터 신뢰도(체크섬, 복구·허용·격리 건수)를 화면 안에 표시
- 데이터를 파일 안에 넣어 **서버 없이 브라우저로 바로 열람** 가능
- 좁은 화면에서 가로로 넘치는 문제 수정

### 이후
"처음 생각 vs 데이터" 구성은 팀원이 완성한 최종 Decision Board의 핵심 구조로 이어졌고, C안은 Gold 데이터와 연결된 상태로 `/gold/`에 남아 있습니다.

### 설명 포인트
- **종합점수를 쓰지 않은 이유**: 가중치를 어떻게 주느냐에 따라 순위가 바뀌어 설득력이 약함 → 실제 단위(초, %)와 상위 %를 그대로 보여주는 편이 검증 가능함

## 3. MySQL 적재 오류 해결 (Silver)

### 문제 1. 1,335행 중 3행만 적재
- **현상**: `repair_detail.csv`를 `LOAD DATA`로 스테이징 테이블에 넣었는데 3행만 들어감. 오류 메시지 없음
- **원인**: 파일 줄바꿈이 윈도우 방식(CRLF, `\r\n`)이고 마지막 칸이 따옴표로 감싸져 있는데, 적재 SQL은 `\n` 기준으로 줄을 나눔 → 줄 경계가 어긋나 여러 행이 한 칸에 붙음
- **해결**: `LINES TERMINATED BY '\r\n'`, `OPTIONALLY ENCLOSED BY '"'`로 수정한 재적재 SQL(`sql/02b_reload_repair_detail.sql`) 작성. 적재 직후 `COUNT(*)`와 `MAX(LENGTH(reason))`을 출력해 행 수와 내용이 온전한지 확인

### 문제 2. MySQL 8.4에서 검증 쿼리 실패
- `ERROR 1137`: 임시 테이블을 한 쿼리에서 두 번 참조 불가 → 일반 작업 테이블(`t_*`)로 변경
- `ERROR 1292`: STRICT 모드에서 빈 문자열을 숫자로 `CAST`하면 오류 → `CASE`로 빈 값을 먼저 처리
- 원본 SQL은 그대로 두고 MySQL 8.4 호환 수정본(`sql/03_validate_cleaned.mysql84.sql`)을 따로 작성

### 설명 포인트
- **CRLF vs LF**: 윈도우는 줄 끝에 `\r\n`, 리눅스·맥은 `\n`을 씀. 파일을 만든 환경과 읽는 설정이 다르면 줄 구분이 깨짐
- **조용한 실패**: 오류 없이 결과만 틀리는 경우가 가장 위험 → 적재 후 원본과 행 수 대사(reconciliation)를 습관화
- **STRICT 모드**: 잘못된 값을 경고 대신 오류로 처리하는 MySQL 설정. 데이터 품질에는 좋지만 빈 값 처리를 명시해야 함

## 4. Django 웹앱 구축 (화면)

### 작업
- Django 5.2 프로젝트 `web/` 생성, MySQL 연결 (접속 정보는 `.env`에서 읽고 Git에서 제외)
- `viewer` 앱 (`/data/`): 적재된 테이블 목록 → 클릭하면 50행씩 조회. SQL 없이 적재 결과를 확인하는 용도
- `dashboard` 앱: Gold 결과를 읽어 Decision Board를 보여주는 화면. 화면에서는 계산하지 않고 읽기만 함
- `run_web.bat` / `run_web_lan.bat`: 더블클릭 실행, 같은 네트워크 다른 PC에서 시연 접속

### 이후
팀원이 파이프라인 관리자(`/ops/`)와 최종 Decision Board(`/`)를 추가했습니다.

### 설명 포인트
- **Django 앱 분리**: 기능별로 앱을 나누면(`viewer`, `dashboard`, `ops`) 서로 영향 없이 수정 가능
- **`.env`로 비밀값 분리**: DB 비밀번호를 코드에 넣으면 저장소에 그대로 공개됨

## 5. Gold 지표 계산 (Gold)

### 작업
- `python web/manage.py build_gold`: MySQL 정규화 스키마에서 데이터를 읽어 Gold 지표를 계산하고 저장하는 Django 관리 명령
- 결과 테이블
  - `gold_driver_profile`: 시즌 × 드라이버 — 페이스(필드 중앙값 대비 %), 팀 동료 대비(초/랩), 일관성(IQR), 타이어 유지(ms/랩), 기본 포인트, 각 지표의 상위 %
  - `gold_team_profile`: 시즌 × 팀 — 팀 지표와 피트 기준값
  - `gold_snapshot`: 화면 한 장에 필요한 값 묶음(JSON)을 실행 시점·출처와 함께 저장
- 클린 랩 규칙: 1랩, 피트 인·아웃 랩, 격리 행, SC·VSC·적기 구간(`race_control` 메시지로 계산), 드라이버 경기 중앙값 107% 초과 랩 제외, 경기당 15랩 이상만 사용

### 설명 포인트
- **왜 Gold를 따로 만드나**: 화면이 열릴 때마다 수십만 랩을 계산하면 느리고 결과도 매번 달라질 수 있음 → 미리 계산해 저장하고 화면은 읽기만
- **클린 랩을 거르는 이유**: 세이프티카 구간이나 피트 랩은 선수 실력과 무관하게 느려서, 섞이면 비교가 불공정해짐
- **스냅샷에 실행 시점·출처를 남기는 이유**: 화면의 숫자가 언제, 어떤 데이터로 계산된 것인지 추적하기 위해

## 회고

### 배운 점
- 데이터 정제의 핵심은 많이 고치는 것이 아니라 **고친 근거와 고치지 않은 이유를 남기는 것**
- 오류 없이 조용히 틀리는 문제가 가장 위험하므로, 단계마다 **행 수와 결과를 대사**해야 함
- Silver → Gold → 화면으로 역할을 나누면 각 단계를 따로 검증하고 다시 실행할 수 있음

### 어려웠던 점
- Gold 단계에서 "그래서 **왜** 이 드라이버인가?"에 답하고 설득하는 부분이 가장 어려웠습니다. 숫자를 보여주는 것과 그 숫자로 결정을 설득하는 것은 다른 일이었습니다.

### 다음에는
- Gold 계산에 쓴 분석 규칙을 처음부터 저장소 안의 코드로 관리해, 누구나 같은 결과를 다시 만들 수 있게 하겠습니다.
- AI 코딩 도구가 만든 코드를 반영하기 전에, 핵심 로직을 직접 설명할 수 있을 때까지 확인하겠습니다.
